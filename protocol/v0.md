# Body-brain protocol, version 0

Status: v0, card P0-05 (13 Nov 2026), revised the same day after an independent review (see section 11; no recordings existed yet, so v0 was changed in place). Machine-readable schema: [`v0.schema.json`](v0.schema.json) (JSON Schema 2020-12). Every JSON example in this file is validated against the schema by `tests/test_protocol_schema.py`, so the doc and the schema cannot drift apart.

The protocol joins a **body** (now an Android phone; later a robot or a simulator) to the **brain** (Python, on the laptop). It is body-agnostic: nothing in it names a particular body, and session recordings (card P1-03) are stored in it. Every body and every recording inherits these rules, so change them only with a version bump (see "Versioning").

Key words: MUST, MUST NOT, SHOULD and MAY are used in their usual RFC 2119 sense.

## 1. Transport

- One WebSocket connection. The brain is the server; the body is the client and always dials out. Default endpoint `ws://127.0.0.1:8765/`.
- During development the phone reaches the laptop through `adb reverse tcp:8765 tcp:8765` (the laptop firewall blocks inbound connections from the phone), so the phone app dials `127.0.0.1:8765`. `python -m brain serve` sets the forward up at start and re-runs it every 60 s, so a dropped adb connection heals by itself once adb is back. The host and port are a setting in the body; a direct WiFi address needs no protocol change, but the phone app allows cleartext `ws://` only to `127.0.0.1` and `localhost`, so it needs a change to the app's network security config and a rebuild, and the brain refuses a non-loopback `--host` unless started with `--allow-remote` (which logs a loud warning).
- **One active body.** The brain serves one authenticated body at a time. When a second body completes authentication, the brain closes the older connection with close code **4001** (replaced). A body that receives 4001 stops reconnecting (otherwise two bodies would knock each other off forever). Replacement happens only after authentication, so an unauthenticated client cannot evict the body.
- **No browsers.** The brain refuses (HTTP 403) any WebSocket upgrade that carries an `Origin` header. Bodies never send one; browsers always do, so no web page open on the laptop can talk to the brain.
- **Unauthenticated connections are limited.** At most 4 connections may be in the handshake at once; more get HTTP 503. Before authentication a frame may be at most 16 KiB (larger closes with 1009); the full limits apply after it. An authenticated body is not affected by either limit. (A local process can still occupy the 4 slots for up to 10 s at a time and so delay a reconnecting body; acceptable on a single-user laptop, noted in section 10.)
- **Text frames** carry exactly one JSON message: UTF-8, at most 65,536 **bytes** (not characters). Numbers MUST be finite: `NaN`, `Infinity` and `-Infinity` are not JSON and are refused as `bad_json`, as is nesting too deep to parse.
- **Binary frames** carry bulk data (image, audio, echo) with the 20-byte header in section 5. A binary frame never travels alone: it is the second half of a JSON message (section 5.2).
- WebSocket-level ping/pong is not used; liveness comes from the protocol heartbeat (section 7). The brain buffers at most 4 received frames per connection before it stops reading (TCP backpressure).
- Close codes: **1000** normal; **1001** the brain is shutting down; **1002** after a fatal protocol error (the sender of the error closes); **1008** authentication failed; **4001** replaced by a newer body.

## 2. Envelope

Every JSON message is one object with exactly these seven fields, all present (use `null` where noted):

| Field | Type | Rule |
| --- | --- | --- |
| `v` | integer | Protocol version. Always `0` in this version |
| `type` | string | One of the message types in section 4 |
| `id` | integer 1 to 2^32-1 | Sender's message number on this connection (section 3) |
| `reply_to` | integer or null | The peer's `id` this message answers, or `null`. Required (non-null) for `ack` |
| `ts_body` | integer 0 to 2^53-1, or null | Microseconds on the body's monotonic clock (section 6) |
| `ts_brain` | integer 0 to 2^53-1, or null | Microseconds on the brain's monotonic clock (section 6) |
| `payload` | object | Type-specific; `{}` when there is nothing to say |

The **sender's own** timestamp field is required: a message from the body MUST have an integer `ts_body`, and one from the brain an integer `ts_brain` (section 6). A message without it is `bad_envelope`.

**Identifiers** chosen by one side and stored by recorders (`boot_id`, `session_id`, `frame_id`, `utterance_id`) match `^[A-Za-z0-9_-][A-Za-z0-9_.-]{0,63}$`: safe as a file name, no path separators, not starting with a dot. `wall_time_utc` is an RFC 3339 UTC timestamp ending in `Z`.

**Free text** from the peer (`hello.software`, `error.message`, `echo.text`, `speak_local.text`) may not contain control characters (U+0000 to U+001F, U+007F), so it cannot forge log lines; both sides also log peer-supplied strings quoted and escaped.

Receivers check the version before anything else, then the type, then the closed envelope, so a message from a newer version gets `unsupported_version`, not `bad_envelope`.

### Unknown-field policy

- **Envelope: closed.** A field that is not in the table above makes the message invalid (`bad_envelope`). New envelope fields require a new version.
- **Payload: open, must-ignore.** A receiver MUST ignore payload fields it does not know. A version-0 sender MAY add optional payload fields; that is a compatible change. Removing a field, changing its meaning or units, or making a new field required is not compatible and requires `v` 1.
- **Names in `hello` are open too.** `hello.capabilities` and `hello.commands` are lists of names (`^[a-z][a-z0-9_]{0,63}$`); a receiver ignores names it does not know, so a newer body can announce a new capability without breaking an older brain.
- **Exception: `command.args` is closed.** Every command's arguments are listed exactly; any extra argument makes the command invalid (`bad_args`). This keeps anything from being smuggled into a command (see section 8). Command **names** are closed too (the allowlist).
- **Closed values:** `audio.encoding` and `image.encoding` stay enumerations. A receiver cannot decode an encoding it does not know, so refusing that one message (`bad_payload`, not fatal) is the correct answer. `sample_rate` is any integer from 8,000 to 192,000 Hz, since any PCM rate can be resampled.

### Versioning

- `v` is an integer that changes only for incompatible changes. A receiver that gets a `v` it does not support replies `error` `unsupported_version` with `fatal: true` and closes.
- Both sides announce the versions they speak in `hello.versions` (optional; absent means `[0]`). The brain refuses a body whose list does not contain 0. In v0 there is only one version, so no negotiation happens beyond that check.

## 3. Ids, replies and ordering

- Each side numbers its own JSON messages on each connection: the first is `id` 1 and each next message is the previous `id` plus 1. Ids restart at 1 on a new connection. Within one connection the pair (sender role, `id`) is unique.
- A receiver SHOULD check that each `id` is the previous one plus 1. A gap means a lost message and MUST be logged (it is not fatal). WebSocket over TCP should never produce one; the echo test counts on this. A body that drops bulk data under backpressure (section 7) drops it before an id is assigned, so drops never show as gaps.
- A binary frame does not get its own id: it carries the `id` of the JSON message it belongs to.
- `reply_to` always names an `id` sent by the peer on the same connection. Replies may arrive in any order relative to other traffic.
- The WebSocket delivers frames in order. A sender MUST send each binary frame immediately after its JSON message, with no other frame in between (implementations hold a send lock across the pair).
- The connection opens with the authenticated handshake of section 4.2: body `hello`, brain `hello`, body `auth`, brain `auth`. Any other message from the body before its `hello` gets `error` `bad_sequence` with `fatal: true`. Neither side sends anything else until the handshake is complete. A second `hello` or `auth` on the same connection gets `bad_sequence` (not fatal) and is ignored.
- `ack` and `error` answer a specific message. `heartbeat` replies and `echo` replies carry `reply_to` as well. Other messages are not answered unless their type says so.

## 4. Message types

Direction: B = body to brain, R = brain to body. A message received in the wrong direction gets `error` `wrong_direction` (not fatal) and is otherwise ignored. `hello.role` MUST match the sender (`bad_payload`, fatal, otherwise).

| Type | Dir | Binary frame | Purpose |
| --- | --- | --- | --- |
| `hello` | B, R | no | Handshake; versions, capabilities, auth nonces |
| `auth` | B, R | no | Each side's proof in the mutual authentication |
| `heartbeat` | B, R | no | Liveness every 2 s and clock-offset samples |
| `pose` | B | no | Body pose at a sensor time |
| `tracking_state` | B | no | Pose tracking became ok, limited or lost |
| `image` | B | yes | One still image, usually answering `capture_image` |
| `audio_in` | B | yes | One chunk of microphone PCM |
| `audio_out` | R | yes | One chunk of PCM for the body's speaker |
| `speak_local` | R | no | Text for the body's own text-to-speech (G1 skeleton only) |
| `event` | B | no | Something happened on the body (data, never an instruction) |
| `command` | R | no | Ask the body to do one allowlisted thing (section 8) |
| `ack` | B, R | no | Success answer to a `command` or another request |
| `error` | B, R | no | Failure answer, or a protocol error |
| `echo` | B, R | optional | Diagnostics: the peer returns the same text and bytes |

`echo` (diagnostics) and `auth` (authentication) were added to the 12 types in the plan.

Capability names known in v0: `pose`, `tracking_state`, `image`, `audio_in`, `audio_out`, `speak_local`, `event`, `echo`.

### 4.1 hello

Body to brain. `boot_id` changes each time the body app starts, so recordings can tell runs apart. `capabilities` lists the message types the body can produce or consume; `commands` lists the allowlisted commands it implements (a subset of section 8). `auth.nonce` is the body's fresh challenge (section 4.2).

```json
{"v": 0, "type": "hello", "id": 1, "reply_to": null, "ts_body": 81234567000, "ts_brain": null,
 "payload": {"role": "body", "software": "embodied-body/0.1.0", "versions": [0], "boot_id": "b-5f2c9a1e",
             "capabilities": ["event", "echo"], "commands": ["get_status"],
             "auth": {"nonce": "8f2d7c1a9b3e4f5061728394a5b6c7d8e9f00112233445566778899aabbccdde"}}}
```

Brain to body, the reply. `session_id` names this connection in brain logs and recordings. `boot_id` changes each time the brain process starts (the body keeps its clock-offset estimate across reconnects to the same brain run). `wall_time_utc` is the brain's wall clock at the same instant as `ts_brain`, which lets recordings map the monotonic clock to calendar time. `heartbeat_ms`, `liveness_timeout_ms` and `max_binary_bytes` tell the body the brain's settings; the body uses them (clamped to the schema's ranges). `auth.nonce` is the brain's fresh challenge. `session_id` and `auth` are required in the brain's hello.

```json
{"v": 0, "type": "hello", "id": 1, "reply_to": 1, "ts_body": null, "ts_brain": 5012345678,
 "payload": {"role": "brain", "software": "embodied-agent-brain/0.0.1", "versions": [0], "boot_id": "r-1c2d3e4f",
             "session_id": "s-20261113-201501-3f9a", "wall_time_utc": "2026-11-13T20:15:01.123456Z",
             "capabilities": ["event", "echo"], "heartbeat_ms": 2000, "liveness_timeout_ms": 6000,
             "max_binary_bytes": 8388608,
             "auth": {"nonce": "0a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8f9"}}}
```

### 4.2 auth (pairing and mutual authentication)

Both endpoints are authenticated before anything else flows, so neither a rogue local app acting as a body (any app with network access can dial `127.0.0.1:8765` on the phone, which `adb reverse` forwards to the brain; any local process can dial the brain) nor one acting as the brain (any app can listen on the phone's port 8765 while `adb reverse` is down) can complete the handshake.

**What it does not do.** The handshake authenticates the two endpoints once. It derives no session key and adds no per-message integrity or encryption. It is therefore sound only where no third party is on the path: loopback on the laptop, and the adb transport between laptop and phone. On any other network (`serve --allow-remote`, a direct WiFi address) an on-path attacker can relay the handshake and then read, inject into or take over the session; that needs TLS or an authenticated encrypted channel first (section 10, question 3).

- **Pairing token.** The brain creates a random 32-byte token on first run in `data/secrets/link_token`. On Windows the `secrets` folder is created first with inheritance removed and access for the current user only (checked after `icacls`, whose exit code is checked), and the file is written inside it under a temporary name and renamed, so it is never readable by others even briefly. The brain refuses to use a token file or folder that another account owns or can open (a planted or exposed token). `python -m brain pair` gives the token to the phone once; `python -m brain pair --rotate` makes a new token first (restart `serve` afterwards; the old token stops working). The phone keeps it in app-private storage that is excluded from backup and device transfer. The token never travels over the protocol and is never logged.
- **Token exposure while pairing.** Laptop: the token is written to adb's standard input, never onto a command line, so other processes, process-creation auditing and endpoint monitoring do not see it. Phone: a shell `read` receives it and passes it to `am broadcast` as an argument, so for a moment it is in that one process's arguments, visible to the adb shell user and root only (apps cannot see other apps' processes). The receiver is debug-build-only and requires `android.permission.DUMP`, a signature|privileged|development permission: the adb shell holds it, as can preinstalled privileged apps and any app that declares it and is granted it with `adb shell pm grant`; ordinary installed apps cannot obtain it on their own. **On-screen pairing must replace this before the microphone streams (P2-02).**
- **Handshake (transcript-bound).** Each side sends a fresh 32-byte nonce (64 lowercase hex characters) in its `hello`. Let `H(x)` be the lowercase hex SHA-256 of a text frame exactly as sent and received (its UTF-8 bytes), and `label` be `embodied-agent v0 body proof` for the body and `embodied-agent v0 brain proof` for the brain. Then
  - the body sends `auth` with `mac = HMAC-SHA256(token, "embodied-agent v0 body proof|" + H(body hello) + "|" + H(brain hello))`;
  - the brain checks it (constant-time) and answers with its own `auth` (`reply_to` = the body's auth) with `mac = HMAC-SHA256(token, "embodied-agent v0 brain proof|" + H(body hello) + "|" + H(brain hello) + "|" + H(body auth))`;
  - the body checks that (constant-time). Only then do heartbeats and everything else start.
- Because the proofs cover the exact hello frames, they bind both nonces, the `session_id` and every hello field (versions, capabilities, commands, boot ids, settings): a changed hello invalidates the proof. Fresh nonces on both sides make a recorded proof useless on a new connection (replay); the role label means one side's proof can never be reflected back as the other's. The body proves itself first; that reveals nothing about the token and is bound to the brain's nonce, so it is useless to anyone else.
- **Failures.** A body hello without `auth.nonce`, or a wrong body `mac`, gets `error` `unauthorized` (fatal) and close **1008**. A body that finds the brain's `mac` wrong sends `unauthorized` (fatal) and closes with 1008. On the body every authentication failure, and every close or error before the handshake completes, counts as one failed connection attempt: it backs off and retries, and gives up after 3 minutes without a stable link (section 7). It never stops on a single unauthenticated message, so an impostor cannot switch it off, and the real brain is found again when the path to it returns. A body with no token does not connect at all and shows "not paired".
- The whole handshake must complete within 10 s.

```json
{"v": 0, "type": "auth", "id": 2, "reply_to": null, "ts_body": 81234590000, "ts_brain": null,
 "payload": {"mac": "9e8d7c6b5a4f3e2d1c0b9a8f7e6d5c4b3a2f1e0d9c8b7a6f5e4d3c2b1a0f9e8d"}}
```

```json
{"v": 0, "type": "auth", "id": 2, "reply_to": 2, "ts_body": null, "ts_brain": 5012367890,
 "payload": {"mac": "4c3b2a19f8e7d6c5b4a39281706f5e4d3c2b1a09f8e7d6c5b4a39281706f5e4d"}}
```

### 4.3 heartbeat

Each side sends a heartbeat request (`reply_to: null`) every 2 s, stamped with its own clock. The peer answers at once with a heartbeat whose `reply_to` is the request `id`, stamped with its own clock **and with the request's timestamp copied into the other clock field**. That reply is one clock-offset sample (section 6). The optional `offset_us` and `rtt_us` report the sender's current estimate, for logs only.

```json
{"v": 0, "type": "heartbeat", "id": 42, "reply_to": null, "ts_body": null, "ts_brain": 5094000000,
 "payload": {}}
```

```json
{"v": 0, "type": "heartbeat", "id": 57, "reply_to": 42, "ts_body": 81316233000, "ts_brain": 5094000000,
 "payload": {"offset_us": 76222231000, "rtt_us": 4100}}
```

### 4.4 pose

The body's pose at sensor time `ts_body`, in the body's current **world frame**, named by `frame_id`.

- **World frame:** right-handed, metres, +y up (opposite gravity), x and z horizontal. Its origin and horizontal heading are wherever the body's tracking started; `frame_id` changes whenever tracking resets and the old frame can no longer be related to the new one (P4 relocalization maps frames together).
- **Body frame** (what `position_m` and `orientation_xyzw` place in the world): origin at the body's reference point; **-z is forward** (the direction the body faces and its main camera looks), +y is the body's up, +x is its right. This is the usual camera convention, so a camera pose can be reported as is.
- `position_m` is the body origin in world coordinates; `orientation_xyzw` is the unit quaternion (x, y, z, w) rotating body-frame vectors into the world frame.
- **Heading:** with `f = R(q) * (0, 0, -1)` the forward vector in world coordinates, `heading_rad = atan2(-f.x, -f.z)`: 0 when facing world -z, increasing counter-clockwise seen from above. The example's quaternion is a 45 degree turn about +y, so its heading is +45 degrees.
- A body whose native frames differ (a phone's sensor frame, a robot's x-forward base frame) converts in its own adapter; the protocol always carries this convention.

Sent at the rate set by `set_pose_rate` (default 10 Hz once implemented).

```json
{"v": 0, "type": "pose", "id": 120, "reply_to": null, "ts_body": 81320100000, "ts_brain": null,
 "payload": {"frame_id": "world-1", "position_m": [0.12, 1.41, -2.03],
             "orientation_xyzw": [0.0, 0.3826834, 0.0, 0.9238795], "tracking": "ok"}}
```

### 4.5 tracking_state

Sent when tracking changes. `reason` is a short snake_case word or null.

```json
{"v": 0, "type": "tracking_state", "id": 121, "reply_to": null, "ts_body": 81320500000, "ts_brain": null,
 "payload": {"state": "limited", "reason": "insufficient_light"}}
```

### 4.6 image

One JPEG still; `ts_body` is the capture time. A binary frame of type `image` with the same `id` and `byte_length` data bytes follows immediately. `pose` is the body pose at capture, if known. When it answers a `capture_image` command, `reply_to` is that command's `id`.

```json
{"v": 0, "type": "image", "id": 130, "reply_to": 88, "ts_body": 81321000000, "ts_brain": null,
 "payload": {"encoding": "jpeg", "width": 640, "height": 480, "byte_length": 48213,
             "pose": {"frame_id": "world-1", "position_m": [0.12, 1.41, -2.03],
                      "orientation_xyzw": [0.0, 0.3826834, 0.0, 0.9238795]}}}
```

### 4.7 audio_in

One chunk of microphone audio; `ts_body` is the time of the first sample. `stream_id` changes for each `start_audio_in`; `seq` counts chunks from 0 within a stream, so a missing chunk (lost, or dropped under backpressure) is visible. 80 ms of 16 kHz mono s16le is 2,560 bytes. A binary frame of type `audio_in` follows.

```json
{"v": 0, "type": "audio_in", "id": 131, "reply_to": null, "ts_body": 81321080000, "ts_brain": null,
 "payload": {"stream_id": 3, "seq": 17, "encoding": "pcm_s16le", "sample_rate": 16000,
             "channels": 1, "byte_length": 2560}}
```

### 4.8 audio_out

One chunk of audio for the body's speaker; `seq` counts from 0 within an utterance and `final: true` marks the last chunk (which may have `byte_length` 0, in which case no binary frame follows). A binary frame of type `audio_out` follows when `byte_length` > 0.

```json
{"v": 0, "type": "audio_out", "id": 90, "reply_to": null, "ts_body": null, "ts_brain": 5100000000,
 "payload": {"utterance_id": "u-12", "seq": 0, "encoding": "pcm_s16le", "sample_rate": 24000,
             "channels": 1, "byte_length": 9600, "final": false}}
```

### 4.9 speak_local

Text for the body's own TTS engine. Used only by the G1 skeleton before streamed TTS (P2-01) exists. The text is spoken, never interpreted.

```json
{"v": 0, "type": "speak_local", "id": 91, "reply_to": null, "ts_body": null, "ts_brain": 5100500000,
 "payload": {"utterance_id": "u-13", "text": "Hello, I can hear you.", "interrupt": false}}
```

### 4.10 event

Something happened on the body. `name` is snake_case; `data` is a small free-form object. Events are information for the brain, never instructions to it: the brain does not execute anything because of an event. Names used so far: `echo_test_result` (end of an echo run), `link_state`, `battery`, `thermal`, `face_present`, `button`. The brain logs event names and data keys; it logs data values only for diagnostics events (`echo_test_result`) or with `--verbose`.

```json
{"v": 0, "type": "event", "id": 140, "reply_to": null, "ts_body": 81330000000, "ts_brain": null,
 "payload": {"name": "echo_test_result",
             "data": {"sent": 1000, "received": 1000, "lost": 0, "corrupt": 0, "bytes_each": 102400}}}
```

### 4.11 command

Brain to body only. See section 8 for the allowlist.

```json
{"v": 0, "type": "command", "id": 88, "reply_to": null, "ts_body": null, "ts_brain": 5096000000,
 "payload": {"name": "capture_image", "args": {"max_edge": 640}}}
```

```json
{"v": 0, "type": "command", "id": 89, "reply_to": null, "ts_body": null, "ts_brain": 5096100000,
 "payload": {"name": "get_status", "args": {}}}
```

### 4.12 ack

Success answer. `reply_to` is required. `result` holds a command's answer, if it has one.

```json
{"v": 0, "type": "ack", "id": 141, "reply_to": 89, "ts_body": 81330100000, "ts_brain": null,
 "payload": {"status": "ok", "result": {"battery_pct": 81, "charging": false}}}
```

### 4.13 error

Failure answer or protocol error. `reply_to` is the offending message's `id` (only when that is a valid id), or `null` when it could not be read. `message` is for humans and logs (at most 500 characters); programs act on `code`. When `fatal` is true the sender closes the connection right after.

```json
{"v": 0, "type": "error", "id": 142, "reply_to": 92, "ts_body": 81330200000, "ts_brain": null,
 "payload": {"code": "unknown_command", "message": "command 'run_shell' is not in the v0 allowlist", "fatal": false}}
```

### 4.14 echo

Diagnostics. Either side may send an echo request (`reply_to: null`); the peer answers with an echo whose `reply_to` is the request `id`, the same `seq` and `text`, and the same bytes in its own binary frame. `crc32` is the CRC-32 (IEEE 802.3, as in zlib) of the data bytes, or 0 when `byte_length` is 0; the receiver checks it and answers `error` `bad_binary` on a mismatch.

```json
{"v": 0, "type": "echo", "id": 200, "reply_to": null, "ts_body": 81340000000, "ts_brain": null,
 "payload": {"seq": 7, "text": "echo 7", "byte_length": 102400, "crc32": 2246129431}}
```

```json
{"v": 0, "type": "echo", "id": 310, "reply_to": 200, "ts_body": null, "ts_brain": 5120000000,
 "payload": {"seq": 7, "text": "echo 7", "byte_length": 102400, "crc32": 2246129431}}
```

## 5. Binary frames

### 5.1 Header layout

All multi-byte fields are **big-endian** (network byte order). The header is exactly 20 bytes, followed by the data.

| Offset | Size | Type | Field | Rule |
| --- | --- | --- | --- | --- |
| 0 | 1 | uint8 | `v` | Protocol version, 0 |
| 1 | 1 | uint8 | `type` | 1 = image, 2 = audio_in, 3 = audio_out, 4 = echo. Others are invalid in v0 |
| 2 | 2 | uint16 | `flags` | Reserved, MUST be 0 when sent; receivers ignore them |
| 4 | 4 | uint32 | `id` | The `id` of the JSON message this frame belongs to |
| 8 | 8 | int64 | `ts` | The sender's timestamp from that JSON message, in microseconds (its `ts_body` or `ts_brain`); 0 to 2^53-1 like the JSON field, so a negative value is `bad_binary` |
| 16 | 4 | uint32 | `length` | Number of data bytes that follow; MUST equal the frame size minus 20 |
| 20 | `length` | bytes | data | JPEG, PCM or echo bytes |

Test vector (also checked by the Python and Kotlin unit tests): an echo frame with `id` 7, `ts` 1234567890123 and data `hello` is

```
00 04 00 00 00 00 00 07 00 00 01 1f 71 fb 04 cb 00 00 00 05 68 65 6c 6c 6f
```

### 5.2 Pairing rules

- The JSON message types `image`, `audio_in`, `audio_out` and `echo` have a `byte_length` field. When it is greater than 0, the very next frame from the same sender MUST be a binary frame whose header has the matching `type` code, the same `id`, the same timestamp and `length` = `byte_length`. When it is 0, no binary frame follows.
- Any mismatch (wrong type, id or length, or a text frame where a binary frame was due) is `bad_binary` with `fatal: true`, because the stream can no longer be trusted. A binary frame that arrives when none was due is `bad_sequence` (not fatal; the frame is dropped).
- The header repeats the type, id and timestamp so that a recording can store binary frames as standalone files and still check them against the JSON log.
- Largest data size: 8,388,608 bytes (8 MiB). Larger is `too_large`, fatal.

## 6. Timestamps and clocks

- Each side stamps only its **own** field with its own **monotonic** clock, in integer **microseconds**: the body sets `ts_body` and leaves `ts_brain` null, and the brain does the reverse. The sender's own field is required (section 2). The only exception to "the other field is null" is a reply that copies the request's timestamp into the other field, which heartbeat replies MUST do.
- The body uses the phone's elapsed-realtime clock (`SystemClock.elapsedRealtimeNanos() / 1000`, which keeps counting in deep sleep). The brain uses Python `time.monotonic_ns() // 1000` (Python 3.13 or later, where Windows uses QueryPerformanceCounter with 1 us resolution; 3.12 ticked in 15.6 ms steps). Neither is wall-clock time and neither jumps when the wall clock is set. Wall time is linked once per connection through `hello.wall_time_utc`.
- For sensor messages (`pose`, `image`, `audio_in`) the timestamp is the sensor time (capture time, or the first audio sample), not the send time. For everything else it is the send time.
- A receiver's arrival time is not part of the message; recorders store it alongside.

### Clock offset

`offset = body clock - brain clock`, so `brain_time = ts_body - offset`.

From a heartbeat the brain sent at brain time `t0` (its `ts_brain`, which the brain remembers per pending heartbeat rather than trusting the echoed copy), answered by the body at body time `t1` (the reply's `ts_body`), and received back at brain time `t3`:

```
rtt    = t3 - t0
sample = t1 - (t0 + t3) / 2        (error at most rtt / 2)
```

**Drift.** The two monotonic clocks run at slightly different rates. Measured on 13 Nov 2026 between the S25 Edge and this laptop: about **-26 to -30 ppm** (the body clock loses about 1.6 to 1.8 ms per minute against the brain's: -28.6 and -29.5 ppm fitted offline from the 13 Nov 16:31 session log, -25.9 ppm fitted live by the brain and +25.5 ppm, brain minus body, by the phone in the 17:10 session). So the true offset changes by about 20 ms every 12 minutes, and "max minus min of the estimate" grows without bound even for a perfect estimator. Each side therefore fits the drift: it takes the lowest-RTT sample of each one-minute bucket over the last 30 minutes, ignores buckets slowed by load (best RTT more than twice the overall best plus 5 ms), and once at least 4 such buckets span at least 4 minutes, fits a weighted least-squares line (weights 1 / (rtt/2 + 1 ms)^2). Fits beyond +/-200 ppm are discarded. Every sample's offset is then projected to the current time along that line.

**Estimator.** The estimate is the projected offset of the sample, among the last 900 (30 minutes at 2 s), with the smallest error bound

```
cost = rtt / 2 + aging * age        aging = 50e-6 before a drift fit exists, 10e-6 after (the fit's residual)
```

An old short-RTT sample therefore outlives a long burst of samples delayed by load: during the first 1,000 x 100 kB echo run RTTs reached 1.35 s and the old "minimum RTT of the last 90 s" filter, whose window then held only delayed samples, stepped about 38 ms; with this estimator the estimate did not move during the echo run. Fresh samples take over as the old one ages.

**Consistency check.** If a new sample's interval (offset +/- rtt/2, which must contain the true offset) cannot overlap the current best's (projected offset +/- rtt/2 + 50e-6 * age), the older samples are wrong for this peer (a bogus sample, or a different body reusing a `boot_id`): they are dropped, the event is logged, and the estimate restarts from the new sample. One bogus sample is therefore undone by the next good one.

**Stability (the acceptance measure).** After a 60 s warm-up, the estimate must change by **less than 20 ms within any 60 s window**. Both sides compute exactly this (`max_change_60s_ms`) and log it in a per-session clock summary when a session ends, including on a normal shutdown, together with the fitted drift, the number of consistency resets and, for information, the whole-session spread (which includes real drift). **Cold start:** the first minute after a fresh process starts is excluded on purpose: until a low-RTT sample arrives the estimate can only be as good as the best RTT so far (the first sample's RTT was 200 ms on 13 Nov), so it moves by up to half that RTT; on the measured link it settled within 30 to 60 s.

The estimator is kept across reconnects while the peer's `boot_id` is unchanged (same body run, same brain run). The brain logs the estimate once a minute at INFO (every sample at DEBUG with `--verbose`).

## 7. Heartbeat, liveness, reconnect, lifecycle and backpressure

- Each side sends a heartbeat request every 2,000 ms after the handshake and answers each peer request at once.
- If either side receives no **valid** frame for 6,000 ms (three missed heartbeats), it treats the connection as dead and drops it. Frames that fail validation do not count, so garbage does not keep a dead or hostile peer alive. The check runs in its own watchdog, separate from sending, so a peer that stops reading (and so blocks our sends) is still detected; a single send that cannot finish within 30 s also aborts the connection.
- More than 20 protocol errors from the peer within one minute make the next one fatal (close 1002).
- The body reconnects automatically after a close or failure, with exponential backoff: 0.5 s, 1 s, 2 s, then 4 s repeated, each with up to 20 % random jitter. The backoff resets only after a link has stayed up for 10 s (a **stable link**), so a brain that accepts and then always closes is not hammered. After the brain restarts, the body is back within about 5 s plus the connection setup, without anyone touching it.
- A connection attempt whose TCP, WebSocket or authentication handshake has not finished within 10 s is abandoned and retried.
- **Body lifecycle.** The body runs the link only after an explicit Connect, and stops it (closing the socket, cancelling all timers, removing its notification and ending its service) on any of: the Stop button or the notification's Stop action; the app being swiped away; **3 minutes without a stable link** (counted from the end of the last link that stayed up 10 s, so a brain that authenticates and then always drops the link does not keep it trying forever); the brain closing an established session with 1001 (shutting down) and not coming back within 60 s; or an established session closed with 4001 (replaced by another body). Closes and errors **before** the handshake completes (including 1008 and `unauthorized`) are failed attempts, never a reason to stop at once, so an unauthenticated peer cannot switch the body off. It is never restarted by the system on its own. While connected it holds a CPU wake lock with a 30 s timeout that each heartbeat reply renews, so the lock lapses by itself if anything stalls; while disconnected it holds none, so in deep sleep its timers pause and the 3-minute give-up can happen later than 3 minutes (at the next wake-up); the link uses no CPU meanwhile, so no alarm is used. A debug build can shorten the give-up time for one run.
- If notifications are not permitted the link still runs; its notification (with the Stop action) is hidden by the system, so the app's screen shows a notice that Stop is available there.
- A new connection is a new session: ids restart and the handshake is exchanged again. The clock estimate is kept only for the same peer run (section 6).
- In-flight requests are not resent after a reconnect; the requester treats them as failed. The brain's `Link.request()` helper takes the expected answer type(s) (for example `ack`, or `image` for `capture_image`), resolves on that type or an `error` with the matching `reply_to`, and fails every pending request with `LinkClosed` when the connection drops, and with a timeout otherwise.
- **Brain handlers.** Messages that are not heartbeats, echoes or answers to a pending request go to the brain's handler in its own task per connection, in order, so a slow handler never delays heartbeats and a handler may await a request to the body. A handler that raises gets the body an `error` `internal` (not fatal) and the session continues. If 256 messages are waiting for the handler, further ones get `busy` and are dropped.
- **Backpressure on the body.** The body's WebSocket library closes the connection if its send queue passes 16 MiB, so bulk data never goes to it blindly. Control messages (`hello`, `auth`, `heartbeat`, `ack`, `error`, `event`) are small and always sent at once, never dropped, so they overtake bulk data that is waiting. Bulk messages (`image`, `audio_in`, `pose`, `echo`) wait in the body's own queue and are handed to the socket only while the socket's queue holds less than 2 MiB; the body's queue holds at most 4 MiB, and when a new bulk message would exceed that, the **oldest** waiting bulk messages are dropped first (fresh sensor data is worth more than stale). One item larger than a cap (an 8 MiB image) still passes when nothing else is queued, but queuing it drops every waiting bulk item. A dropped message gets no id, so it shows as a `seq` gap in `audio_in`, never as an id gap. **Notes for P2-02 (audio):** an `ack` for `start_audio_in` can arrive before audio chunks queued earlier; one large image drops all queued audio; audio may need its own small queue or priority. The brain side relies on TCP backpressure plus the 30 s send timeout.

## 8. Command boundary

The plan's "Command boundary" section says the app channel teaches but never commands the system. The protocol enforces its share of that in code:

1. **Only the brain sends `command`.** A `command` arriving at the brain from a body is answered with `wrong_direction` and is not acted on. Nothing a body sends (text, speech, images, events) is ever executed by the brain; it is data.
2. **Commands are an enumerated allowlist, default deny.** The body MUST answer any `command` whose `name` is not in the table below with `error` `unknown_command` and do nothing else. A listed command the body has not implemented yet gets `not_implemented`.
3. **Arguments are closed and typed.** Each command's `args` are exactly the ones listed, as numbers within bounds. Extra or wrongly typed arguments get `bad_args`. No argument is a free-form string.
4. **Nothing in the protocol carries a file path, a shell string, or a query about the host system.** There is no message type for files, processes, settings, logs or the network. `speak_local.text` is spoken aloud, `event` names and data are information, and `echo` bytes are opaque test data; none is interpreted as an instruction.
5. **Only an authenticated brain can command the body, and only an authenticated body can feed the brain** (section 4.2), within the limits stated there: the endpoints are proven once, which holds on loopback and the adb transport; on any other path it needs transport security first (section 10, question 3).
6. **Adding a command** means adding it to `v0.schema.json` (`$defs.command_name` and its `args` rule), to this table, to `COMMANDS` in `brain/transport/protocol.py` and to `Protocol.COMMANDS` in the body. Tests check that the Python list, the Kotlin list, the Kotlin argument bounds and the schema agree.

| Command | Args | Body answers | Purpose | Implemented in |
| --- | --- | --- | --- | --- |
| `get_status` | none (`{}`) | `ack` with `result` {battery_pct, charging, ...} | Read-only body status | P0-05 (minimal) |
| `capture_image` | `max_edge`: integer 64 to 4096 | `image` with `reply_to` = command id | Take one still | P1-01 |
| `start_audio_in` | none | `ack`, then `audio_in` chunks | Start the mic stream | P2-02 |
| `stop_audio_in` | none | `ack` | Stop the mic stream | P2-02 |
| `stop_audio_out` | none | `ack` | Stop speaker output now (barge-in, stop) | P2-01 |
| `set_pose_rate` | `hz`: number 0 to 30 (0 = off) | `ack` | Pose stream rate | P1-02 |

## 9. Errors

`error.payload.code` is one of:

| Code | Meaning | Fatal |
| --- | --- | --- |
| `bad_json` | A text frame is not a JSON object (including NaN or Infinity, or nesting too deep) | no |
| `bad_envelope` | Envelope fields missing, wrong type, or unknown; or the sender's own timestamp missing | no |
| `bad_payload` | Payload does not match its type's schema | no (yes for a wrong `hello.role`) |
| `unsupported_version` | `v` is not 0, or the peer's `hello.versions` lacks 0 | yes |
| `unknown_type` | `type` is not a v0 type | no |
| `wrong_direction` | Type not allowed from this sender (for example `command` from a body) | no |
| `bad_sequence` | Message before or instead of the handshake, second hello or auth, or a binary frame that was not due | yes during the handshake, otherwise no |
| `bad_binary` | Binary header invalid or does not match its JSON message, or CRC mismatch on echo | yes for a header mismatch, no for a CRC mismatch |
| `too_large` | Frame over the size limits in sections 1 and 5 | yes |
| `unknown_command` | Command name not in the allowlist | no |
| `bad_args` | Command arguments missing, extra or out of range | no |
| `not_implemented` | Allowlisted command or capability not built yet | no |
| `busy` | Valid request the receiver cannot serve now (for example camera in use, or the brain's handler queue is full) | no |
| `internal` | Receiver failed while handling a valid message | no |
| `unauthorized` | Not paired, or authentication failed (section 4.2) | yes (close 1008) |

The receiver of an `error` logs it. It never answers an `error` with another `error`, not even an invalid one, which prevents loops. Implementations validate their own outgoing messages against the schema before sending, so they never emit an invalid message (for example an `error` whose `reply_to` copies an out-of-range id).

## 10. Open questions

1. Recording format (P1-03): store JSON lines plus one file per binary frame, or one container file? The protocol does not decide this, but recordings must keep every envelope unchanged.
2. Should the brain also be able to resume a session after a reconnect (keep `session_id`)? v0 says no: each connection is a session.
3. Transport encryption and channel binding. Authentication (section 4.2) proves the endpoints once; traffic is plain `ws://` with no per-message integrity. That is sound over loopback and the adb transport (no third party on the path) and **not** on any other network, where an on-path attacker can relay the handshake and then read, inject or hijack. **Required before camera or microphone data crosses anything but loopback or adb:** TLS (`wss://` with a pinned self-signed certificate) or an authenticated encrypted channel with a key derived from the handshake.
4. Video or a higher-rate image stream would need credit-based flow control on top of the drop-oldest queue in section 7; v0 assumes stills at 1 to 2 Hz and audio at 12.5 chunks per second.
5. Whether `pose` should switch to a compact binary form if 30 Hz is ever needed.
6. Why the brain-to-body delay on the `adb reverse` wireless link ramps from about 10 ms to 140 ms over a minute and then resets (seen on 13 Nov 2026 with the phone idle and its screen locked; WiFi power saving or adb transport buffering are the suspects). It matters for audio latency (G4) more than for the clock offset, which the aged minimum-RTT estimator absorbs.
7. Token lifetime: `python -m brain pair --rotate` replaces the token (and the phone must be paired again); there is no automatic expiry.
8. Pairing over adb is a development mechanism (section 4.2 lists its exposure). **On-screen pairing (a code shown by the brain and confirmed on the phone, or a QR code) is required before the microphone streams (P2-02)**, and the debug receiver must not be relied on beyond development.
9. The phone keeps the token in app-private SharedPreferences, excluded from backup and device transfer but not wrapped by the Android Keystore; wrapping it (an AES key in the Keystore) would protect it from a rooted-device file read. Not built.
10. A local process can hold the 4 pending-handshake slots (section 1) and so delay a reconnecting body by up to 10 s at a time. Acceptable on a single-user laptop; a per-address limit would be needed on a shared host.
11. `python -m brain probe` connects as a body, so it replaces a connected phone (4001) and the phone stops until Connect is pressed again. It warns; a distinct diagnostics role was not added.
## 11. Decisions

Made in the first draft of v0:

- Integer ids that count up by one per sender per connection, so loss is visible, rather than UUIDs.
- Integer microseconds of monotonic clocks, one field per side, rather than wall-clock milliseconds; wall time is linked once per connection in `hello`.
- Binary data as a separate binary frame tied to a JSON header message by `id`, rather than base64 in JSON (33 % larger and slow) or a binary-only protocol (hard to read in logs).
- Envelope closed, payloads must-ignore, command arguments closed.
- `echo` added as a diagnostics type.

Changed in place after the independent review of 13 Nov 2026 (no recordings or other bodies existed, so no version bump):

- `hello.capabilities` and `hello.commands` became lists of names rather than enumerations, so an unknown name is ignored instead of fatal; command names stay an enumeration in `command`. Encodings stay enumerations (an unknown encoding cannot be decoded); `sample_rate` became an integer range.
- The sender's own timestamp is required; timestamps are 0 to 2^53-1 in JSON and in the binary header.
- NaN and Infinity are refused; the 64 KiB text limit counts UTF-8 bytes.
- Identifiers that a recorder may use as file names got a safe pattern; `wall_time_utc` got a timestamp pattern.
- The pose frame is defined (section 4.4), including forward axis and heading.
- `hello.versions` added (the text promised it; there was no field) and a brain `boot_id`.
- Requests carrying an `Origin` header are refused.
- One active body; the newest authenticated one replaces the older (4001), and the replaced body stops.
- Brain handlers run off the receive loop; handler exceptions answer `internal`; a request helper with timeouts and fail-all on disconnect.
- Liveness has its own watchdog and counts only valid frames; sends have a timeout; more than 20 protocol errors a minute are fatal.
- The clock estimator changed from "minimum RTT of the last 90 s" to the aged minimum over 30 minutes, kept across reconnects of the same peer runs.
- Mutual HMAC authentication with a pairing token, the `auth` message type and the `unauthorized` error code (section 4.2); a non-loopback brain address needs an explicit flag.
- Body lifecycle (explicit start and stop, 3-minute unreachable stop, wake lock only while connected) and body-side backpressure with drop-oldest for bulk data (section 7).
- The body's adb test hook moved from intent extras on the exported main screen to a debug-build-only broadcast receiver that requires `android.permission.DUMP` (signature|privileged|development: the adb shell, preinstalled privileged apps, or an app granted it with `pm grant`), with capped echo sizes.

Changed in place after the second review (13 to 14 Nov 2026; still no recordings, so no version bump):

- The handshake became hello / hello / auth / auth: each proof is an HMAC over the SHA-256 of the exact handshake frames (the transcript), so it binds every hello field, both nonces and the session id; the brain's proof moved from its hello to its own `auth`. The spec now says plainly that this authenticates endpoints only, with no session key or per-message integrity.
- Stability of the clock estimate is defined as "less than 20 ms change within any 60 s window after a 60 s warm-up" and logged by both sides; the clocks' drift is fitted and the estimate projected along it; a consistency check drops samples that cannot be right for this peer.
- The token moved to `data/secrets/` (private folder created before the file; ACL, owner and `icacls` exit code checked; foreign or exposed files refused), is delivered on adb's stdin instead of a command line, and can be rotated.
- Free-text fields may not contain control characters; peer strings are logged quoted.
- Before the handshake completes, closes and errors (including 4001, 1008 and `unauthorized`) are failed attempts for the body, never a stop; 4001 and 1001 count only on an established session. The give-up clock counts time without a stable link.
- At most 4 pending handshakes; 16 KiB frame limit before authentication.
- `Link.request()` takes the expected answer type.
- The phone app excludes its data from backup and device transfer, and shows a notice when notifications are off.
